# UseCase: DeleteLead — Удалить лид (soft delete)

## Что решает

Помечает лид как удалённый (`is_deleted = True`). Лид исчезает из всех списков и Kanban-доски. Операция необратима в стандартном интерфейсе (восстановление только через БД или отдельный административный инструмент).

**Статус:** ❌ Не реализовано (планируется — Приоритет 1)

---

## Участники

| Поле | Значение |
|------|----------|
| **Actor** | Менеджер или выше |
| **Роли** | `sales_manager`, `director`, `admin` |

---

## Входные данные

| Поле | Тип | Описание |
|------|-----|----------|
| `lead_id` | `UUID` | ID лида |

---

## Порядок действий

```
1. Открыть Unit of Work

2. Загрузить лид из БД
   └─ Если не найден → LeadNotFoundError

3. Проверить права через политику:
   - Consultant не может удалять лиды
   └─ Если нет прав → PermissionError

4. Вызвать lead.delete()
   └─ Устанавливает is_deleted = True

5. Сохранить лид в БД

6. Создать LeadTimelineEvent "lead_deleted" (автоматически)

7. Зафиксировать транзакцию (commit)
```

---

## Возможные ошибки

| Ошибка | Условие |
|--------|---------|
| `LeadNotFoundError` | Лид не найден |
| `PermissionError` | Нет прав на удаление |

---

## Результат

`None` — успешное выполнение.

---

## Бизнес-правила

- `is_deleted = True` — **необратимо** через стандартный UI (в отличие от архивации)
- Удалённые лиды не отображаются **нигде** в интерфейсе
- Задачи, комментарии и события timeline, связанные с лидом, физически остаются в БД — они просто недоступны через UI
- **Consultant** не может удалять лиды — только менеджеры и выше

> Важно: в PRD зафиксировано разграничение `is_archived` (скрыт, восстанавливаем) vs `is_deleted` (удалён). Удалять нужно осторожно.
