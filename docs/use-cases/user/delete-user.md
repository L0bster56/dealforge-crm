# UseCase: DeleteUser — Деактивировать пользователя

## Что решает

Деактивирует пользователя — устанавливает `is_active = false`. Физического удаления из БД не происходит (soft delete через флаг активности). Деактивированный пользователь теряет доступ к системе: токены перестают работать при следующем запросе.

**Файл:** `backend/src/backend/application/user/use_cases/delete_user.py`

**Статус:** ✅ Реализовано

---

## Участники

| Поле | Значение |
|------|----------|
| **Actor** | Администратор системы |
| **Роли** | `admin` |

---

## Входные данные (`DeleteUserCommand`)

| Поле | Тип | Описание |
|------|-----|----------|
| `user_id` | `UUID` | ID пользователя для деактивации |

---

## Порядок действий

```
1. Открыть Unit of Work
2. Загрузить пользователя из БД по user_id
   └─ Если не найден → ошибка UserNotFoundError
3. Проверить права актора через CanDeleteUserPolicy
   │  Правила:
   │  - нельзя деактивировать самого себя
   │  - нельзя деактивировать пользователей с ролью выше своей
   └─ Если нет прав → ошибка PermissionError
4. Вызвать репозиторий users.delete(user) 
   (физическое удаление ИЛИ is_active=false — зависит от реализации)
5. Зафиксировать транзакцию (commit)
```

---

## Возможные ошибки

| Ошибка | Условие |
|--------|---------|
| `UserNotFoundError` | Пользователь не найден |
| `PermissionError` | Попытка деактивировать самого себя или более привилегированного пользователя |

---

## Результат

`None` — успешное выполнение без возвращаемого значения.

---

## Бизнес-правила

- Администратор **не может деактивировать себя** — защита от случайной блокировки единственного администратора
- Деактивация — обратимая операция: администратор может повторно активировать пользователя (механизм активации не реализован отдельным use case в текущей версии, делается через `UpdateUser`)
- Все активные JWT-токены деактивированного пользователя **не инвалидируются немедленно** — они будут отклонены при следующей проверке `is_active` в `GetMe` или `RefreshToken`
